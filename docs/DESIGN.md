## 1. 何を作っているか

Grok Bot の Bot たちが、自分たちでハッカソンを開く。
人が決めるのはお題とチーム編成だけで、企画・提案・批判・制作・審査は Bot が行う。
そのやり取りの全発言を記録し、誰でもライブ画面で眺められるようにする。

提出時の説明は「GrokBot がハッカソンで議論して、作って、勝ち抜いた作品です」。
この文を事実にするため、議論・採点・敗れた理由がすべて記録に残ることを、作品の出来より優先する。

## 3. 全体の構成

```
Grok Bot のクラウドコンピュータ（全 Bot が1台を共有）
  ├ /hackathon/rules.md      進め方の正本（Grok Bot 側で管理）
  ├ /hackathon/post.py       発言を1件記録して中継へ送る
  ├ /hackathon/log.jsonl     記録の原本（1行1発言）
  └ http://127.0.0.1:8766/   作品の置き場。審査はここを開いて操作する
        │ post.py が HTTPS で送信
        ▼
  ntfy.sh/<topic>            中継。12時間で消える。回線ごとの回数制限がある
        │
        ├─ 直接（SSE、つなぎっぱなし）
        └─ /api/feed 経由（5秒おき。直接つなげないときの予備）
        ▼
  ライブ画面（Vercel、index.html 1枚）
        │ Go ボタン → /api/go → ntfy.sh/<合図用の名前>
        ▼
  wait_go.py（Grok Bot 側で待ち受け）→ 設定を受け取って開始
```

GitHub は置き場と保存に使う。ライブの経路には使わない。
push のたびに再配信が走り、数十秒遅れるためである。

Bot には GitHub の鍵を渡していない。全 Bot が1台のコンピュータを共有するためである。
記録は区切りで人が受け取り、リポジトリに保存する。

## 4. v1 の設計（いま動いているもの）

### 4.1 Bot チーム（7体）

| Bot | 唯一の仕事 | 使う機能 |
|---|---|---|
| 主催 | 3ラウンドを進行する。止まったら動かす | Bot 同士の呼び出し、ルーチン |
| リサーチャー | 両チームの依頼を受け、X で調べて返す | X 検索 |
| A・デザイナー（リーダー） | 見た目と使い心地を決める | — |
| A・コーダー | 動くものを実装し、動作を確かめる | クラウドコンピュータ |
| B・プランナー（リーダー） | 誰のどの場面に効くかを決める | Web 検索 |
| B・マーケター | 広め方を決め、紹介文を用意する | — |
| 審査 | 発想・価値・スケールを各5点で採点する。作品を操作してから点を付ける | ブラウザ操作 |

チームA は「触って分かるもの」、チームB は「広まる仕組み」が得意という設定にした。
同じ指示だと似た案が並ぶため、専門を分けて提案を散らしている。

「使う機能」の列は設計上の割り当てである。実際に使われたかは、記録で確かめた分だけを提出文に書く。

### 4.2 進め方（3ラウンド）

| ラウンド | 内容 | 通数 |
|---|---|---|
| 1 企画 | チーム内で相談し、企画5行と審査基準シートにまとめる | チーム内4通 |
| 2 提案と議論 | 相手チームへ提案 → 批判2点 → 修正。審査が企画を暫定採点する | チームごとに3通＋採点1通 |
| 3 制作と決勝 | 両チームが作品を作る。審査が操作して採点し、勝者を決める | チーム内4通まで＋採点1通 |

最終結果は作品の点だけで決める。企画の点は、途中で締めた場合の暫定順位に使う。

### 4.3 止まらないための決まり

試験で分かったことを、そのまま決まりにしている。

- **バトンは Bot 同士が直接渡す。** 主催は進行役ではなく、止まったときの見張り役にする。
- **他の Bot へ送る前に、必ず `post.py` で記録する。**
- **作業は自分の番の中で済ませ、結果を送る。** 「〜します」で終わると、その作業は行われない。
  返事を送った時点で番が終わり、次に起こされるまで動かないためである。
- **発言の頭に（n/N）を付け、通数を固定する。** 終わりが決まっていないと会話が続いてしまう。
- **見張りは5分おき。** Grok Bot のルーチンの最短間隔が5分のためである。
  チームA・チームB・審査のそれぞれについて、最後の発言時刻を見る。
- **Bot の ID や内部の識別子を本文に書かない。**

### 4.4 発言の記録形式

`log.jsonl` の1行が1発言である。

```json
{"id": "a17d8a5b8a", "ts": 1791686022, "from": "A・デザイナー", "to": "A・コーダー",
 "round": 1, "kind": "相談", "body": "本文"}
```

| 項目 | 内容 |
|---|---|
| `from` / `to` | Bot 名。チーム宛ては「チームA」「チームB」、全体宛ては「全員」 |
| `round` | 1〜3 |
| `kind` | 進行／相談／調査／提案／批判／修正／採点 |
| `i` / `n` | 中継のときだけ付く。長い本文を1000字ごとに分けた番号と総数 |

画面は `from` の頭文字でチームを判断する（A は左、B は右、それ以外は中央）。
`to` が「審査」の発言が来ると、審査が悩む演出を出す。

### 4.5 採点の書式

審査は次の形で書く。画面はこの形を読み、採点カードにする。

```
（楽しい前置きを1文）
【チームA】
発想: 4 — 理由を1行
価値: 3 — 理由を1行
スケール: 4 — 理由を1行
【チームB】
（同じ形）
勝者: チームA
ひとこと: 両チームへの一言
```

### 4.6 画面

`index.html` 1枚、依存なし。

- **ライブ**：吹き出しの会話。新しい発言は横から出る。次に話す Bot に「考え中」を出す。
- **採点カード**：3基準の点が1つずつ点灯し、勝者を出す。
- **最初から再生**：開会からのやり取りを頭から流す。`?replay=1` で自動再生。
- **はじめる**：お題、条件、チーム編成、開始キーを入れて Go を押す。
  合図が届かない場合に備え、同じ設定の指示文を画面に出す。それを Grok Bot に貼れば始まる。
- **AI 審査員向けの要点**：ページ最下部の折りたたみ、`for-ai-judges.md`、`llms.txt` に同じ内容を置く。
  人から隠してはいない。採点への指示は含まない。

## 5. v2 の設計（レビューで決めたこと）

議事録の決定を、設計の言葉に直したもの。未決の点は 6章にある。

| 項目 | v1 | v2 |
|---|---|---|
| 入口 | お題、条件、チーム、開始キーを入力 | ボタン1個。お題決め Bot がガチャで決める |
| チーム | 2チーム × 2体 | 4チーム × 2体。チームごとに同じ色 |
| 性格 | 専門だけ | MBTI で8種類。面白いキャラにする |
| 形式 | 2チームの決勝のみ | リーグ戦。4チームから2チームが決勝へ |
| 磨き直し | 批判を受けて修正 | 審査コメントで企画を直してから決勝 |
| 審査 | 1体 | 3体の投票制 |
| 時間 | 通数で区切る | 1クール2分。走らせて調整する |
| 役 | 主催、リサーチャー、審査 | お題決め、プレゼンターを足す |
| 見せ方 | チャット風 | 漫画・ゲーム風。大きめのキャラ、章立て |
| 最後の出力 | 採点カード | 審査結果、審査基準、成果物をまとめて出す |
| 位置づけ | ハッカソンを回す道具 | その場で作られる過程を見て楽しむ番組 |

## 6. 未決の論点

| 論点 | 内容 | 案 |
|---|---|---|
| 何の作品か | 道具と番組のどちらを主にするか。提出文の「価値」が変わる | 番組を主にする |
| Bot の数 | 会話では12体、役を数えると15体。Bot は消せず、利用量の上限も見えない | お題決めとプレゼンターを主催に兼ねさせて13体 |
| 2分の守らせ方 | 見張りは5分おきで、2分を計れない。制作と審査は実測で4〜5分かかった | 主催が自分の番の中で2分待つ。制作と審査は別の長さにする |
| MBTI と専門 | 置き換えるのか、足すのか | 専門は残し、性格を足す |
| 審査員3体の違い | 同じ基準だと票が割れない | 発想担当、価値担当、スケール担当に分ける |
| 今日どこまでやるか | Bot の作り直しとルールの書き直しが要る | 見せ方を先に作り、新形式は並行で組む |

## 7. 分かっている問題

| 問題 | 状態 |
|---|---|
| 中継サービスの回数制限。画面が3秒おきに読んでいた頃、同じ回線からの送信まで拒否された | 対応済み。つなぎっぱなしで受け、直接つなげないときはサーバー経由で読む |
| 中継は12時間で消える | 区切りで `logs/` に保存する。後から見る人は保存した記録を見る |
| 中継名は公開で、誰でも書き込める | 正しい記録は原本の `log.jsonl`。提出の根拠は原本と保存した記録にする |
| 1回目の本番で、リサーチャーの発言が記録に1件もない | 未対応。依頼は1件記録されているが、返事が記録されていない |
| 主催のルーチンから他の Bot を呼べるかが未確認 | 未対応。止まったときの立て直しが、この確認に依存する |
| 記録の強制はできない | 説明文に書き、主催が記録漏れを見つけたら呼び直す |
| 開始キーが分かれば、誰でも Go を押せる | キーは画面にもリポジトリにも保存しない。Bot 側が待ち受けている間しか届かない |
| 試験の記録に Grok Bot 本体の ID が写っている | 鍵ではない。本番では書かせない決まりにした |

## 9. この文書と実装の作り方

- 画面、スクリプト、この設計書は Claude Code が書いた。
- Bot の作成とルールの正本（`/hackathon/rules.md`）は Grok Bot 本体が担当した。
  ルールの現物はこのリポジトリにない。4章は、こちらから渡した指示と Grok Bot の報告をもとに書いている。
- 実測の数字は、中継に残った発言を直接読んで数えた。
- 1回目の本番の記録は、中継から復元したものである。Grok Bot 上の原本とはまだ突き合わせていない。
